# Деплой на camp.offline-tambov.ru

## Что где живёт

Штаб и ресепшен работают **по адресу домена** и правят файлы прямо на
сервере. Значит источник правды — сервер, а не ноутбук.

| | Ноутбук | Сервер |
|---|---|---|
| `landing.html` | образец для нового лагеря | **живая версия**, её правит штаб |
| `participants.json` | резервная копия | **живые карточки** целиком, со взносами |
| `integrations.json` | копия | **живой**, токены ботов |
| `signups.json` | резервная копия | копится от телефонов |
| `admin.html`, `reception.html` | код, правится руками | приезжает из git |

**Ноутбук в повседневной работе не нужен вообще.** Доступ заводится в
Supabase (аккаунт) и в таблице `staff` (роль), участники появляются через
панель, лендинг правится там же, история — в `backups/` на сервере. Ноутбук нужен только
для правок кода: `./deploy/publish.sh code`.

Локальный режим (`node server.mjs 8000`, панели на `localhost`) остаётся
рабочим и по файлам в папке — но это автономный запас на случай «интернета
нет совсем», а не часть обычного круга.

## Адреса

| | |
|---|---|
| https://camp.offline-tambov.ru/ | лендинг, участникам |
| https://camp.offline-tambov.ru/enter.html | **вход** — одна дверь на всех |
| https://camp.offline-tambov.ru/admin/ | штаб (301 на дверь) |
| https://camp.offline-tambov.ru/reseption/ | ресепшен (301 на дверь) |

## Вход

**Одна дверь.** Открываете `/enter.html`, вводите логин и пароль, и вас
приводит туда, где работает ваша роль: регистратуру — на стойку, всех
остальных — в штаб. Ни адреса проекта, ни ключа `anon` вводить не нужно:
их отдаёт сервер. Ничего не настраивается на каждом новом устройстве.

Старые адреса `/admin/` и `/reseption/` остались и ведут на дверь: они в
закладках браузеров и записаны на бумаге в лагере. Больше того: открытая
без входа `admin.html` тоже приводит на дверь, а открытая не по роли — в
ту панель, которая этой роли подходит. Пустых страниц «Не найдено» на
пути человека больше нет — они остались только для данных, где 404
нарочно не подсказывает, существует ли файл.

### Два входа, один порядок

Дверь одна, но лагерь может жить и без интернета — поэтому у неё два
режима. Какой сейчас, она спрашивает у сервера (`GET /dbconfig` → поле
`mode`), а не угадывает:

| | `mode:'db'` — есть Supabase | `mode:'file'` — базы нет |
|---|---|---|
| что спрашивает дверь | e-mail и пароль | **логин** и пароль |
| кто держит пароли | Supabase Auth | `users.json` рядом с панелью |
| кто их сверяет | Supabase | сам `server.mjs` |
| откуда роль | таблица `staff`, живая | `users.json`, поле `role` |
| откуда данные | база, права по RLS | файлы в папке |

Правило **«или — или»**, и оно важнее удобства: база настроена — файл не
читается вовсе; базы нет — только файл. Два действующих списка доступа
одновременно означали бы два разных ответа на вопрос «кто здесь
главный», а сходиться им негде.

Пароль в обоих режимах проверяется **не в браузере**. Раньше `users.json`
уезжал в панель и хэши сверялись там же — это честно называлось слабым
местом: клиентскую проверку обходят инструментами разработчика. Теперь
файл с хэшами не отдаётся по HTTP **вообще никому и ни в каком режиме** —
даже главному, даже с `127.0.0.1`. Браузеру он больше не нужен ни для
чего.

Параметры хэша те же, что были (PBKDF2-SHA256, 120 000 итераций, соль как
строка), так что **старые пароли из `users.json` продолжают работать**.
Совпадение закреплено в `node auth.mjs --selftest` вектором, снятым с
настоящего `crypto.subtle`.

### Почему не два пароля, как было

Раньше `/admin/` и `/reseption/` были разными портами под разными файлами
`htpasswd`, и **роль определялась паролем**. Схема была честная, но у неё
есть следствие, которое не обойти: `auth_basic` в nginx срабатывает *до*
того, как отдан первый байт. То есть роль выбиралась раньше, чем могла
загрузиться страница входа, — и «одна дверь, которая сама определяет
роль» при таком порядке невозможна в принципе. Пароль **был** ролью.

Поэтому порядок обратный: сначала человек входит, потом сервер узнаёт его
роль и только после этого решает, что отдавать. Разделение доступа при
этом не ослабло, а усилилось — оно переехало на уровень ниже, где
покрывает и `PUT`, и `/queue`, чего пароль на всю смену не делал.

```
enter.html ──Supabase Auth──> токен ──POST /session──> server.mjs
                                                          │ проверяет токен у Supabase
                                                          │ читает роль из staff
                                                          ▼
                                          кука: uid|роль|срок + подпись HMAC
                                          HttpOnly, SameSite=Lax, 12 часов
```

Подпись — на секрете, выведенном из `SUPABASE_SERVICE_KEY`; секрет не
покидает сервер. Без базы брать его негде, поэтому он рождается случайным
при запуске и живёт только в памяти: перезапустили сервер — все вошедшие
входят заново. Для панели на ноутбуке это скорее плюс (на диске секрета
нет вовсе), а кому мешает — задаёт `CAMP_SECRET` и получает сессии,
переживающие перезапуск. Подменить в куке роль или срок нельзя, не сломав подпись
(проверяется в `node auth.mjs --selftest`). Кука `HttpOnly` именно потому,
что обычный переход по ссылке на `admin.html` заголовок не несёт — а
заголовку и не поверили бы.

**Роль в куке — снимок на момент входа.** Отозвали доступ — кука доживёт
до срока, поэтому срок короткий (смена). Всё, что вправе делать роль с
данными, всё равно проверяет база своими политиками RLS в момент запроса,
а не эта кука.

### Что видно какой роли

Роли приходят из таблицы `staff`, и их четыре, а не две: пока роль была
портом, «вожатый» и «редактор» получали весь штаб — у них был пароль от
`/admin/`.

| | Главный | Вожатый | Редактор | Регистратура | Без входа |
|---|---|---|---|---|---|
| `admin.html` | видит | видит | видит | **404** | **404** |
| `reception.html` | видит | видит | **404** | видит | **404** |
| `enter.html`, лендинг, иконки | видит | видит | видит | видит | видит |
| `users.json` (хэши) | **404** | **404** | **404** | **404** | **404** |
| участники | пишет | пишет | **404** | пишет | **404** |
| `landing.html` (запись) | пишет | пишет | пишет | **404** | — |
| токены ботов | пишет | **404** | **404** | **404** | **404** |

С единой базой **зеркала базы по HTTP не отдаются никому**, включая
главного: `participants.json`, `signups.json`, `integrations.json`,
`camp.json`, `outbox.json` — служебные копии для сервера и ботов, а панели
берут эти данные из базы под правами, которые RLS проверяет в момент
запроса. Файл же отдался бы любому, у кого на руках ещё живая кука.

Без базы (лагерь на файлах) наоборот: эти файлы и есть данные, панель
работает прямо с ними, и запрет не применяется. Кроме `users.json` — он
закрыт всегда: хэши паролей не рабочие данные ни при каком режиме.

## Как это устроено

```
                    ┌─ / ──────────────── лендинг (белый список)
камп.домен ─ nginx ─┼─ /enter.html ────── дверь (тоже белый список)
                    ├─ POST /session ──── вход, лимит частоты
                    └─ всё прочее ─────── порт 8000, роль из куки

ноутбук ──git push──> GitHub ──git pull (2 мин)──> сервер   (только КОД)
ноутбук <──── rsync ──────────────────────────────  сервер   (копия ДАННЫХ)
```

`server.mjs` слушает **один** порт. Портов было три — 8001 для штаба и
8002 для стойки существовали ровно потому, что роль определялась портом.
Роль теперь в куке, и второй с третьим стали способом сказать то же
самое дважды.

| Кто приходит | Что доступно |
|---|---|
| без куки | белый список: лендинг, воркер, манифест, иконки, дверь и `camp-db.js`, плюс `/seats`, `/signup`, `/me`, `/camp`, `/dbconfig`, `POST /session` |
| с кукой | то, что положено роли (таблица выше), плюс `PUT`, `/queue` и `GET /whoami` |

Порт слушает только loopback: наружу смотрит nginx. **Но пропуском порт
больше не является** — им стала подписанная кука. Заголовку («я штаб»)
верить по-прежнему не приходится: подделать подписанную куку нельзя, а
незаверенный заголовок можно, и цена ошибки здесь вся админка.

`PUT` разрешён по имени файла и по роли: `landing.html` — главному,
вожатому и редактору, участники — главному, вожатому и стойке, токены
ботов — только главному. Всё остальное 403. `server.mjs`, `sw.js` и
`bots.mjs` правит только человек через git: `PUT` туда означал бы
удалённое исполнение кода на сервере.

`GET /dbconfig` отдаёт адрес проекта и ключ `anon` — публично, и это
нормально ровно по одной причине: **у роли `anon` в схеме нет ни одной
политики RLS и ни одного `grant execute`** на функции с `security
definer` (`claim_seat`, `whoami` — они обходят RLS, и выданные `anon`
превратились бы в оракул «есть ли такой номер в лагере», отвечающий
именем и комнатой). Это проверяется в `supabase/schema.test.sql`. Выдадите
`anon` хоть одну политику — маршрут в ту же секунду станет дырой.

Сервер к тому же отказывается отдавать ключ, у которого внутри JWT роль
не `anon`: перепутать `anon` и `service_role` в `/etc/camp.env` — опечатка
на одну строку, а последствие было бы «ключ в обход всех прав уехал
каждому, кто спросит».

Сервер тянет код сам, а не GitHub заходит по SSH. Репозиторий публичный,
поэтому `git pull` не требует никаких секретов — а схема с Actions
потребовала бы держать SSH-ключ к серверу в GitHub Secrets, то есть взлом
аккаунта GitHub означал бы root здесь.

Рабочая копия и раздаваемая папка разделены намеренно:

| | | |
|---|---|---|
| `/srv/camp-src` | клон репозитория | тут лежат и старые копии лендинга |
| `/srv/camp` | что видит сервер | только нужное, плюс живые данные |


## Первая установка

Нужен **Node 20.11 или новее**: `server.mjs` использует
`import.meta.dirname`. В Debian 12 и Ubuntu 24.04 `apt install nodejs`
ставит 18.x — сервер откажется стартовать и скажет об этом. Поэтому Node
берём из NodeSource, а не из системного репозитория.

```bash
# на сервере, под root
curl -fsSL https://deb.nodesource.com/setup_22.x | bash -
apt install -y nodejs nginx certbot python3-certbot-nginx git rsync
node -v                                   # должно быть v22.x, не v18
# --group обязателен: без него adduser --system кладёт camp в nogroup,
# группы camp не появляется, и chown camp:camp падает — а следом за ним
# каждая выкладка, потому что pull.sh делает install -o camp -g camp
adduser --system --group --home /srv/camp --shell /bin/bash camp
mkdir -p /srv/camp && chown -R camp:camp /srv/camp
git clone https://github.com/vlad4endev/camp-2026 /srv/camp-src
```

Сервис и таймер выкладки:

```bash
cp /srv/camp-src/deploy/camp.service      /etc/systemd/system/
cp /srv/camp-src/deploy/camp-pull.service /etc/systemd/system/
cp /srv/camp-src/deploy/camp-pull.timer   /etc/systemd/system/
systemctl daemon-reload
systemctl enable camp
/srv/camp-src/deploy/pull.sh              # первая выкладка, поднимет camp
systemctl enable --now camp-pull.timer
```

`pull.sh` сам поймёт, что запущен впервые: в `/srv/camp` ещё нет лендинга.
Дальше он выкладывает только при новом коммите в `main`.

Прокси и сертификат. `A`-запись `camp` → IP сервера должна быть
**до** этого шага: certbot проверяет домен по HTTP-01, то есть Let's
Encrypt должен достучаться до этого сервера по имени.

```bash
cp /srv/camp-src/deploy/nginx.conf /etc/nginx/sites-available/camp.offline-tambov.ru
ln -sf /etc/nginx/sites-available/camp.offline-tambov.ru /etc/nginx/sites-enabled/
rm -f /etc/nginx/sites-enabled/default      # чтобы наш server_name стал основным
nginx -t && systemctl reload nginx          # пройдёт: TLS в конфиге ещё нет
certbot --nginx -d camp.offline-tambov.ru   # допишет 443, ssl_* и редирект с 80
nginx -t && systemctl reload nginx
```

Конфиг лежит без TLS намеренно: объявить `listen 443 ssl` заранее нельзя —
`nginx -t` упал бы на отсутствующем сертификате, а certbot прогоняет
`nginx -t` перед работой и отказался бы стартовать.

**В `nginx.conf` только ASCII.** Это единственный файл проекта с
английскими комментариями: плагин `certbot --nginx` парсит все конфиги
nginx, и кириллица в них роняет его с `UnicodeDecodeError`. Сломался бы не
только выпуск сертификата, но и `certbot renew` через 90 дней — молча.

### Ключи Supabase

Без них вход не выдаётся никому — панели останутся закрытыми. Файл
**не** в git, читает его только root:

```bash
sudo install -m600 -o root -g root /dev/null /etc/camp.env
sudo tee /etc/camp.env >/dev/null <<'EOF'
SUPABASE_URL=https://xxxx.supabase.co
SUPABASE_ANON_KEY=eyJhbGci…
SUPABASE_SERVICE_KEY=eyJhbGci…
EOF
sudo systemctl restart camp
```

Все три — в Supabase: Project Settings → API. `SERVICE_KEY` работает ещё и
секретом подписи куки входа, поэтому его смена разом обнуляет все сессии
(это нормально и иногда полезно).

Проверить, что сервер отдаёт панелям настройки и не отдаёт лишнего:

```bash
curl -s https://camp.offline-tambov.ru/dbconfig
```

Ждём `{"mode":"db","url":…,"anon":…}`. Ответ `{"error":"not_anon"}` значит,
что в `SUPABASE_ANON_KEY` попал не тот ключ (скорее всего `service_role`) —
сервер отказался его отдавать. Ответ `{"mode":"file"}` — переменных нет
вовсе, и лагерь работает по файлам: вход пойдёт по `users.json`.

### Кто входит

Пароли держит **Supabase Auth**, в папке лагеря их нет и быть не может.
Поэтому человека заводят в Supabase → Authentication → Users, а роль ему
выдают в таблице `staff` (или из штаба, раздел «Пользователи», если вы уже
там главный). Ролей четыре: `admin`, `lead`, `desk`, `content`.

Отдельной команды на сервере для этого больше нет — `deploy/mkuser.mjs`
удалён вместе с `users.json` и его PBKDF2. Панель **по-прежнему намеренно
не даёт завести доступ самому себе**: на публичном адресе «стать
главным» было бы захватом штаба тем, кто открыл его первым. Только теперь
эту границу держит база (политика `staff_write` — правит лишь `admin`), а
не отсутствие кнопки. Последнего активного `admin` база не даст ни
разжаловать, ни отключить, ни удалить — за этим следит триггер
`staff_keep_admin`, и его не обойти запросом мимо панели.

Пароля **nginx** на панелях больше нет. Он был первым слоем, пока вход
внутри панели был клиентским (его обходят через инструменты разработчика)
и пока за паролем лежали `users.json` и карточки участников. Сейчас
проверку делает сервер до отдачи файла, а данные приходят из базы под
правами роли — так что `htpasswd` стал третьим забором вокруг того же
поля. Если вы обновляетесь со старой схемы, файлы можно убрать:

```bash
rm -f /etc/nginx/camp-admin.htpasswd /etc/nginx/camp-desk.htpasswd
```

Участников заливать не нужно — `pull.sh` создаёт пустой `participants.json`
при первом запуске, дальше их вносит панель или ресепшен.

## Проверка, что граница держит

После установки — обязательно, это главный риск деплоя.

Без входа не отдаётся ничего, кроме лендинга и двери:

```bash
for p in "" enter.html camp-db.js admin.html reception.html users.json participants.json signups.json integrations.json camp.json outbox.json server.mjs; do printf "%-22s %s\n" "/$p" "$(curl -so /dev/null -w '%{http_code}' https://camp.offline-tambov.ru/$p)"; done
```

`200` на первых трёх строках (лендинг, дверь, её скрипт), дальше везде
`404`. Если `200` даёт `admin.html` — проверьте, что сервис запущен с
`CAMP_PUBLIC=1`; если его даёт любой `.json` — что `/etc/camp.env` на
месте и база включена (без базы файлы и есть данные, см. выше).

Дверь работает и отдаёт настройки:

```bash
curl -s https://camp.offline-tambov.ru/dbconfig
```

Ждём `{"url":…,"anon":…}` — и ключ с ролью `anon`, а не `service_role`
(сервер это проверяет сам, но посмотрите глазами хотя бы раз):

```bash
curl -s https://camp.offline-tambov.ru/dbconfig | sed 's/.*"anon":"[^.]*\.\([^.]*\).*/\1/' | base64 -d 2>/dev/null; echo
```

Вход без токена не выдаёт куку — это главная проверка этого раздела:

```bash
curl -si -X POST -H 'Content-Type: application/json' -d '{"access":"подделка"}' https://camp.offline-tambov.ru/session | grep -iE '^HTTP|set-cookie'
```

Ждём `401` и **ни одного** `Set-Cookie`. Если кука пришла — вход выдаёт
права по присланному, а не по проверенному, и это дыра во весь штаб.

Записи и очередь без входа не принимаются:

```bash
printf 'PUT лендинга: %s (ждём 405)\n' "$(curl -so /dev/null -w '%{http_code}' -X PUT -d x https://camp.offline-tambov.ru/landing.html)"
printf 'POST /queue:  %s (ждём 404)\n' "$(curl -so /dev/null -w '%{http_code}' -X POST -d '{}' https://camp.offline-tambov.ru/queue)"
```

Разделение ролей проверяется уже с входом: зайдите под регистратурой и
убедитесь, что `/admin.html` отдаёт `404`, а `/reception.html` — `200`.
Ту же границу без сервера проверяет `node server.mjs --selftest`
(раздел «ЧЕТЫРЕ РОЛИ ИЗ staff»), а подпись куки — `node auth.mjs
--selftest`: подменить в ней роль или срок нельзя.

Порт сервера не должен торчать в интернет напрямую:

```bash
curl -s -m 5 -o /dev/null -w '%{http_code}\n' http://camp.offline-tambov.ru:8000/admin.html || echo "порт 8000 снаружи закрыт — так и надо"
```

Если `admin.html` отдаётся по публичному адресу — забыт `CAMP_PUBLIC=1`.
Без него `server.mjs` считает каждый запрос из-за nginx запросом
организатора: nginx стоит на той же машине, и все соединения приходят с
127.0.0.1. Проверяется в selftest (`на домене loopback привилегий не даёт`).


## Повседневная работа

Всё в панели по адресу домена: расписание, объявления, мастер-классы,
участники, оплаты. Сохранение уходит на сервер сразу, участники видят правки
при следующем открытии страницы — версия кэша в `sw.js` считается из хэша
лендинга и меняется сама.

История правок — на сервере, в `backups/`: 20 последних состояний лендинга и
20 списков участников. Снимок делается на каждое сохранение.
`integrations.json` не снимается намеренно — множить по папке копии
токенов ботов незачем.

```bash
ls -lt /srv/camp/backups/ | head
```

Новый человек в панель: аккаунт в Supabase → Authentication → Users,
затем роль в таблице `staff` (или из штаба, раздел «Пользователи»).
На сервере для этого делать нечего.

С ноутбука — только правки кода:

```bash
./deploy/publish.sh code
```

Копия данных на ноутбук (не обязательно, сервер сам себе источник правды):

```bash
./deploy/publish.sh pull
```

Что происходит на сервере:

```bash
ssh root@camp.offline-tambov.ru 'journalctl -u camp-pull -n 30 --no-pager'
```

Выложить код принудительно, не дожидаясь таймера:

```bash
ssh root@camp.offline-tambov.ru '/srv/camp-src/deploy/pull.sh --force'
```


## Боты

Ставятся на тот же сервер, рядом:

```bash
TG_TOKEN=… MAX_TOKEN=… CAMP_PORT=8000 node bots.mjs
```

Они ходят на `http://127.0.0.1:8000/signup` — то есть внутрь, минуя nginx
и его лимиты. Так и надо: бот уже знает, кто к нему пришёл.

## Чего здесь нет

- **Синхронизации ноутбука и сервера.** Правьте в панели на домене. Локальная
  панель на `localhost` работает по файлам в папке и о сервере не знает: если
  править в обеих, версии разойдутся молча. `publish.sh pull` — это резервная
  копия, а не слияние; `publish.sh restore` — путь обратно, только для пустого
  сервера, и он спрашивает, прежде чем затереть.
- **`landing.html` из git.** Раз его правит панель на сервере, это уже живое
  состояние, а не код. `pull.sh` ставит его из репозитория **один раз**, когда
  файла ещё нет; дальше git-версия остаётся образцом для нового лагеря.
  Поэтому история правок лендинга живёт в `backups/` на сервере, а не в
  коммитах.
- **Ролей больше четырёх.** Их четыре — `admin`, `lead`, `desk`,
  `content`, — и живут они в двух местах: списки файлов в `server.mjs`
  (`READ`/`WRITE`) и политики RLS в `supabase/schema.sql`. Пятая роль
  добавляется правкой обоих, руками. Портов и `location` для этого больше
  не нужно — роль приходит из куки, а не из двери.
- **Откатов через GitHub.** Сервер всегда выкладывает `origin/main`. Чтобы
  откатить код, нужен `git revert` и push. Сломанный код туда не попадёт —
  его отсекает selftest в `pull.sh`.
- **Бэкапов сервера наружу.** `backups/` на сервере наполняется снимками
  участников и лендинга, но никуда не уезжает. `./deploy/publish.sh pull`
  забирает текущее состояние; для настоящих бэкапов настройте `restic`.
- **Приватного репозитория.** `git clone` идёт без секретов именно потому,
  что репозиторий публичный. Сделаете приватным — понадобится deploy key на
  сервере и адрес `git@github.com:vlad4endev/camp-2026.git`.
