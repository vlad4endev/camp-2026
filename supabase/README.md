# Единая база лагеря на Supabase

Одна база на весь проект: штаб, стойка, лендинг и боты работают с одними
данными. Штаб и стойка — с любого устройства, лендинг и боты — через
`server.mjs`, как и раньше.

**Панелям база обязательна**: вход в штаб и на стойку идёт через Supabase
Auth, файлового входа больше нет. **Серверу — нет**: без переменных
окружения `db.mjs` выключен, и `server.mjs` работает на JSON-файлах ровно
как до него. Это же его поведение, когда база недоступна.

## Что где лежит

| Было | Стало |
|---|---|
| `participants.json` | таблицы `participants` + `payments` |
| `signups.json` | таблица `signups` |
| блок `CAMP` в `landing.html` | `camp_content.doc` (одна строка-документ) |
| `users.json` (PBKDF2) | Supabase Auth + таблица `staff` (роль и e-mail) |
| `integrations.json` | таблица `integrations` (видит только `admin`) |
| `rooms.json` | таблица `rooms` |
| `bots.json` | остаётся у бота; привязки отражаются в `bot_links` |

Файлы `participants.json`, `signups.json` и новый `camp.json` остаются на
диске — теперь это **зеркало** базы, из которого читает `server.mjs`.
Поэтому лагерь работает без интернета, а `PUBLIC_FILES` и `--selftest`
не пришлось переучивать.

## Установка

**1. Создайте проект** на supabase.com. Из Project Settings → API
понадобятся: `URL`, ключ `anon`, ключ `service_role`.

**2. Примените схему.** SQL Editor → вставьте `schema.sql` → Run.
Файл идемпотентный, повторный прогон ничего не теряет.

**3. Перенесите данные** — с ноутбука, где лежат живые файлы:

```bash
SUPABASE_URL=https://xxxx.supabase.co SUPABASE_SERVICE_KEY=… node supabase/import.mjs --dry
```

`--dry` только считает и печатает, ничего не записывая. Убедились в
числах — уберите флаг и запустите снова.

**4. Заведите людей** в Authentication → Users → Add user, каждому
e-mail и пароль. Пароли из `users.json` не переезжают: их хэши Supabase
Auth не примет, и это правильно — пароли не должны лежать в папке
лагеря. Скрипт из шага 3 напечатает готовые строки для этого шага.

**Первому** роль придётся выдать руками — панель войти ещё не даст
(uuid виден в списке Users):

```sql
insert into staff (user_id, email, name, role)
values ('…uuid из Auth…', 'natalya@example.com', 'Наталья', 'admin');
```

Первая строка обязана быть `admin`: база не даст оставить штаб без
активного главного, а управлять доступом может только он. Дальше
остальных добавляет сам штаб — раздел «Пользователи», кнопка
«+ Человек в штаб» (нужны e-mail и uuid из Supabase).

Кнопки «создать аккаунт» в панели нет намеренно: на публичном адресе
«стать главным» было бы захватом штаба тем, кто открыл его первым.
Панель выдаёт только роль уже существующему аккаунту.

Без строки в `staff` вход не даёт **ничего**: ключ `anon` сам по себе не
открывает ни одной таблицы. Это проверяется в `schema.test.sql`.

Роли: `admin` — всё; `desk` — стойка, участники и взносы; `lead` —
участники и записи; `content` — только расписание и тексты, персональных
данных не видит вовсе.

Последнего активного `admin` база не даст ни разжаловать, ни отключить,
ни удалить: без него никто больше не сможет выдать роль обратно. Передать
роль можно — сначала назначить второго главного, потом разжаловать себя.

**5. Включите базу на сервере.** В юните `camp.service` (см.
`deploy/README.md`):

```
Environment=SUPABASE_URL=https://xxxx.supabase.co
Environment=SUPABASE_SERVICE_KEY=…
```

**6. Включите базу в панелях.** Откройте штаб → на экране входа
«Подключить единую базу» → адрес проекта и ключ **anon**. Стойка
подхватит те же настройки: тот же браузер, тот же origin.

## Ключи: что куда

| Ключ | Где живёт | Что даёт |
|---|---|---|
| `anon` | браузер: штаб, стойка | ничего сам по себе, доступ решает RLS по `staff` |
| `service_role` | только `server.mjs` и `bots.mjs` | обходит RLS полностью |

`service_role` в браузер вводить нельзя, и панель это проверяет: она
смотрит поле `role` внутри JWT и отказывается принять чужой ключ. Иначе
перепутать их было бы легко, а заметить — нечем.

Ключ `anon` панель держит в `localStorage` этого браузера, токены входа —
в `sessionStorage`: закрыли вкладку — вход сброшен.

## Что происходит без интернета

Лагерь работает. `server.mjs` держит зеркало и отвечает телефонам из
него, а записи на мастер-классы складывает в `outbox.json` и досылает,
когда связь вернётся.

Панели пробуют Supabase напрямую; не вышло — стучатся в локальный
`POST /queue`, и очередью занимается сервер. В ответе приходит
`queued: true`, и панель это **показывает**: «связи нет, уйдёт в базу,
когда появится». Молчать здесь нельзя — на стойке это деньги.

Досылка безопасна при повторе: запись на мастер-класс упирается в
`unique (who, cls)`, взнос — в свой `id`, придуманный на устройстве.
Это свойство схемы, а не аккуратность кода.

Единственный честно возможный отказ при досылке — «мест уже нет»:
пока лагерь был без сети, группу могли добить онлайн. Такие операции
`flush()` не прячет, а называет в логе.

## Пароли

Их нет ни в репозитории, ни в папке лагеря, ни в панели. Забыл пароль —
сброс письмом из Supabase (Authentication → Users) или новый пароль там же.
Панель пароли не видит и менять не умеет.

Файл `users.json` и команда `deploy/mkuser.mjs` удалены: два списка
доступа означали бы два разных ответа на вопрос «кто здесь главный», и
сходиться им было бы негде.

## Что стало лучше, чем на файлах

**Лимит мест теперь настоящий.** Раньше между «посчитали занятые места»
и «записали» помещался чужой запрос: на 12 мест могло прийти 13 человек.
`claim_seat` проверяет и вставляет в одной транзакции, а
advisory-блокировка выстраивает одновременные записи в одной группе в
очередь.

**Деньги не теряются при одновременной правке.** Взносы — строки в своей
таблице, а не массив внутри участника. Два устройства не могут затереть
друг друга: раньше это спасала только дисциплина «перечитать → поменять
одного → записать».

**Права проверяет база, а не интерфейс.** `content` не видит телефонов и
взносов, даже если открыть раздел вручную. И штаб не остаётся без
главного: это триггер в базе, а не кнопка, которую обойдёт запрос мимо
панели.

**Пароли ушли из папки лагеря.** Раньше `users.json` с хэшами PBKDF2
приходилось отдавать ещё и стойке — вход шёл по нему же. Теперь отдавать
нечего.

## Проверки

```bash
node db.mjs --selftest        # перевод полей и механика очереди
node server.mjs --selftest    # границы доступа и лимиты
```

Схема проверяется на настоящем Postgres. В Supabase `auth.users` и
`auth.uid()` уже есть, локально нужен шим:

```bash
initdb -D /tmp/camp-pg -U postgres --auth=trust
LC_ALL=C postgres -D /tmp/camp-pg -p 55432 -k /tmp/camp-pg &
```

```sql
-- /tmp/camp-shim.sql
create schema if not exists auth;
create table if not exists auth.users (id uuid primary key, email text);
create role anon; create role authenticated; create role service_role;
create or replace function auth.uid() returns uuid language sql stable as
  $f$ select nullif(current_setting('request.jwt.claim.sub', true), '')::uuid $f$;
grant usage on schema public to anon, authenticated, service_role;
```

```bash
psql -h /tmp/camp-pg -p 55432 -U postgres -f /tmp/camp-shim.sql
psql -h /tmp/camp-pg -p 55432 -U postgres -f supabase/schema.sql
psql -h /tmp/camp-pg -p 55432 -U postgres -f supabase/schema.test.sql
```

Фикстура в `schema.test.sql` взята из `server.mjs --selftest` дословно:
правило «один человек не занимает два места» переехало из JS в SQL, и
разойтись им нельзя. Тест откатывает транзакцию, данные не остаются.

## Чего эта база не делает

**Не удаляет.** Ни `import.mjs`, ни сохранение из штаба не убирают из
базы того, кто исчез из списка: случайная пропажа строки не должна
уносить человека вместе со всеми его взносами. Штаб про это говорит и
предлагает удалять по одному.

**Не хранит словарь редактора.** Цвета меток, типы событий и набор
значков по-прежнему разбираются из разметки `landing.html`. Панель,
открытая через сервер, получает её обычным `fetch`; совсем без разметки
расписание править можно, но метки и значки будут пустыми.

**Не делает `landing.html` ненужным.** Он остаётся тем, что уезжает в
GitHub и раздаётся участникам. Разница в том, что телефоны берут
расписание из `GET /camp`, то есть из базы, — поэтому правка с планшета
доезжает до участников и без файла.
